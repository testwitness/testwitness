# Design

This page explains the decisions behind testwitness and what is deliberately out of scope. The rule catalogue is in the rules reference; the measured precision is in [precision.md](./precision.md).

## The question the tool answers

A reviewer looking at a pull request wants to know two things about its tests: do they still prove anything, and did they run. CI answers neither. A green check means the tests that ran passed; it says nothing about tests that were deleted, skipped, loosened, mocked out or never collected, and nothing about a PR description that says "all tests pass" when no test ran. testwitness reads three inputs the PR already has, the git diff, the test source and the JUnit XML, and puts the answer on the PR.

## Three states, not two

The check reports `pass`, `review` or `unreadable`. It never says a PR lied.

The reason is empirical. In the one published audit of "tests pass" claims against transcripts, 117 of 124 claims had a run behind them, and the 7 without one were unreadable output rather than lies. pr-witness's author reports that on a frozen batch of 17 real commits its accusing verdict was wrong every time while its "review" verdict was right every time. A tool that accuses honest work is turned off within a week. So the strongest statement testwitness makes is "this PR changed what its tests prove, a reviewer should look", and a claim that cannot be checked is reported as unreadable, with the reporter to turn on, not as false.

## Diff scoped

Rules run on what the PR changed, never on the whole repository. A repository with two hundred pre existing skipped tests gets no finding until a PR adds one. This is the single largest false positive control and the main difference from Sonar, tsDetect and the eslint jest rules, which lint the whole tree and know nothing about the base, the head or the test run.

## Deterministic, no model

Every finding comes from a rule that can be read, tested and argued with: a tree-sitter query, a diff pattern or a comparison of two inventories. There is no model call. Cheap detectors beat model judges on this task in the published comparison (five model judges never exceeded AUROC 0.65 while TF-IDF detectors reached 0.83 and 0.95), they cost nothing per run, they work offline, and they can be explained in a code review. Each finding carries the rule id, the file and line, the before and after text and a one line reason.

## Precision over recall

A rule ships only when its false positive rate on the corpus is acceptable, and every rule's false positive controls are written before its detector. Concretely, R001 (test deleted) stays low when the test was moved (same body or same name elsewhere in the PR), folded into a parameterised test, rewritten (other changed test files gained as many tests as the PR deleted), replaced in its own class or group, or refactored (every assertion survives). A deletion is medium or high only when none of those signals is present. The same discipline applies to A001 (consolidation, assertions moved to a sibling, parameterised, replaced by call) and A002 (a stronger assertion on a sub expression). The replaced by call control exists because a helper is often defined in a file the PR does not touch, or that is not on disk at all, so the inventory cannot see that `result.did_create(path)` asserts. Each front end records every call in a test body and marks the ones that are a whole statement. When a changed test lost assertions and gained at least as many new call statements, A001 drops one step (medium to low, high to medium) and labels the finding replaced by call, naming the first new callee. A call statement is new when its callee name is called nowhere in the base body, it is not on the line of an assertion, and it is not a print, log or sleep call (`print`, `console.*`, `logging.*`, `logger.*`, `System.out.*`, `Thread.sleep` and the like). The finding stays visible in the collapsed low list because the helper may not assert at all. Since the helper index (below), a helper in a test support file of the checkout that does assert is counted as an assertion, so this control is left for helpers the index cannot see or cannot read as asserting. Severity defaults keep anything context dependent at medium or low, so a single uncertain rule cannot drive the check to review on its own.

The corpus (`corpus/`) holds patches from real public pull requests under permissive licences, most of them honest refactors chosen because a naive detector would flag them. It is split by hash of the URL into a tuning half and a held out half; precision is published on the held out half. Every user reported false positive becomes a corpus entry before the fix merges.

## JUnit XML is the contract

The evidence join (V003, V004, V006) reads JUnit XML because every runner in the three languages can write it: Surefire and Gradle do by default, pytest with `--junitxml`, Jest with jest-junit, Vitest and Playwright with their junit reporters, Mocha with mocha-junit-reporter. JUnit XML is not one standard; the reader relies only on the elements and attributes all producers agree on (`testsuite/@name`, `testcase/@name`, `@classname`, `@file`, and the child elements `skipped`, `failure`, `error`, `flakyFailure`, `flakyError`, `rerunFailure`, `rerunError`) and carries a fixture produced by running each real producer (`fixtures/*/junit/`). Name normalisation strips parametrisation suffixes and understands each producer's `classname` shape. What is lost by this choice: per assertion detail that framework specific hooks could give. What is gained: three languages and seven runners through one parser, and a tool that works on any CI.

## Configuration and coverage as text

C001, C002 and C003 compare what the runner and coverage configuration let through, base against head. Each format goes through a real parser: YAML, JSON, TOML (smol-toml, bundled), INI as configparser reads it, Java properties and XML (saxes, DTDs never fetched). JavaScript and TypeScript configs are never imported: a literal reader takes object and array literals, strings, numbers, booleans and regular expression literals at the key it is asked for and treats any other expression as opaque, so `[...configDefaults.exclude, 'src/legacy/**']` reads as one new pattern. Gradle scripts are read with regular expressions inside test task blocks, as W003 reads them. Exclusions are matched against the test files of the head tree, so a finding can say how many test files a pattern drops, and a pattern that drops none is low with the label matches nothing.

## Proven rules and the cap

Every rule runs on every change, but v0.1 reports only four of them at medium or high: R003, R004, R005 and A002 (`PROVEN_RULES` in `packages/core/src/proven.ts`). Findings of every other rule are capped at low in one place, after all rules ran and the configured severities were applied, and before acknowledgements, the state and the summary are computed. Each capped finding keeps the rule's own severity in `uncappedSeverity`, so the corpus keeps measuring what every rule would say. W006, the gate protecting itself, is the one exception. A repository opts a rule back in by naming its severity in `.testwitness.yml`. Why the line is drawn there: [how we measure precision](./how-we-measure-precision#proven-and-unproven-rules).

## Why the AST and why tree-sitter

Diff text alone cannot tell a deleted test from a moved one, a loosened assertion from a reformatted one, or a test from a helper. The engine parses the base and head versions of every changed test file into a `TestInventory` (tests, containers, markers, assertions with a strength rank, mocks, body hash, statement count) and the rules compare inventories. tree-sitter gives one parser architecture for Java, TypeScript, JavaScript and Python as wasm grammars loaded by `web-tree-sitter`, no native compile on the runner, and queries in `.scm` files that a contributor can extend without touching the engine. Framework knowledge lives in tables (test call names, skip and focus modifiers, assertion shapes, the strength lattice, mock shapes), not in code.

## Helpers in other files

Tests often assert through project helpers: a `result.did_create(path)` method in `tests/lib`, a base class method such as `assertQuery`, a `checkMeta` function in a sibling module, a custom matcher. Name based reading catches the ones called `assert*` or `check*`. The rest used to need `assertions.extra`, and without it O001 reported tests whose only oracle is such a helper, and A001 could only lower a replacement to low with the label replaced by call. The helper index reads those helpers instead.

**When it runs.** Only when a changed test (added, modified or renamed, base and head) makes a call that could be a project helper: a whole statement call, not on the line of an assertion, not a print, log or sleep call, not a framework, mock, timer, lifecycle, collection or browser action call (`when`, `spyOn`, `useFakeTimers`, `push`, `click` and the like), and not an assertion helper of the file itself. A PR whose tests make no such call never builds the index.

**What it scans.** The working tree at `cwd`, which is the PR head in the Action and the local repository for the CLI. Only test support locations: files under any directory named `test`, `tests`, `__tests__`, `spec`, `testing`, `test-utils`, `testutils` or `fixtures`, every `conftest.py`, and so `src/test/**` for Java, with an extension one of the enabled front ends parses. `.git`, `node_modules`, virtual environments and `paths.ignore` are not entered and symbolic links are never followed. Files whose name says helper, util, support, assert, matcher, base or conftest are taken first. The scan stops at 2,000 files or 50 MB, skips single files over 1 MB, and records a warning in the report (`helperIndex.warnings`, and the Helpers in other files section of the comment) when a cap is hit.

**What it parses.** Lazily, by name. The index needs every definition of the names the changed tests call, and a definition always contains its own name, so only support files that mention one of those names are parsed, with the same front end that parses test files. Each front end reports every function and method defined outside a test: its name, its class, the assertions written directly in its body (framework, name based, `assertions.extra`) and the names of the calls it makes as statements. For definitions without an assertion of their own, the names they call are indexed in a second pass, so a helper that calls a helper that asserts counts. That is depth 2 from the test; there is no third level, so cycles cannot loop. Parsing is all it does: nothing is imported, required or executed.

**How a call resolves.** By the callee's simple name: `result.did_create(...)` looks up `did_create`. A bare or `self`, `this` or `cls` call to a name the test file defines is that definition. When the name exists in the index both with and without an assertion, and the call is a bare or self call, a definition on the test class or one of its superclasses (as declared in the test file and the indexed files) decides. Otherwise the call counts: a helper named like this that contains an assertion somewhere is more likely an assertion than not. The receiver's declared type is not tracked. A resolved call becomes a custom assertion with family `helper`, the strength of the strongest assertion inside, and `resolvedVia: 'helper-index'` with the helper's name, file and line, so the report can say "counted via helper did_create in tests/lib/__init__.py" (`helperIndex.resolved` in the JSON report). The checks inside the helper are not compared by A002; a helper in the same file still is.

**What it changes.** O001 is silent for a new test whose only oracle is such a helper. A001 reads inline assertions replaced by calls to such helpers as a helper extraction and is silent, as it already was for helpers in the same file. A helper with no assertion the front end can read (only prints, returns, or a plain `throw`) is not counted: O001 still fires and A001 keeps the replaced by call label.

**Cost and cache.** A support file that is also a changed test file of the PR, with the same content at head and on disk, reuses the inventory the run already built. On the 1,000 file benchmark (`pnpm bench`, two cores) the new tests without an assertion call `total()`, so the index is built: 200 support files, all of them changed test files, resolved in 64 to 90 ms, and the median wall time stayed within noise of the run before the index (13.86 s before, 14.07 s after, budget 30 s). Before that reuse existed the same run parsed the 200 files again, which took about 1 second cold. Parsed definitions are cached per file, keyed by path, size and modification time, in a JSON file in a per user directory under `os.tmpdir()` (`testwitness-helper-index-<uid>`, owner only), named by a hash of the checkout's real path, the tool version, `assertions.extra` and the enabled extensions. A cache is written only when parsing took at least 200 ms, so small repositories leave nothing behind. The cache is never read from or written to the checkout: a file under `node_modules/.cache` in the working tree is something a pull request can commit, and a forged entry could make an empty helper count as an assertion. In the Action every run is a fresh runner, so the cache is best effort there.

**Limits.** Helpers outside the scanned locations, helpers in packages that are not on disk (published test kits, other repositories), and helpers that fail with a plain `throw` still need `assertions.extra`. In the corpus only the changed files of each pull request are on disk, so the index can only find helpers that the pull request itself touched.

## Security posture

The Action runs on `pull_request` with `permissions: contents: read`. It needs no secrets and the engine makes no network calls: grammars and parsers are bundled. The Action's only network calls go to the GitHub REST API with the job token: the optional comment and the acknowledgements, each of which fails soft. It never executes repository code: no install, no test run, no `require` of config files; runner configs are parsed as text or AST and only literal values are read. The helper index parses test support files of the checkout the same way, follows no symbolic links, and keeps its cache outside the checkout. Configuration is read from the base ref in PR mode, so a PR cannot relax its own check (W006 reports any attempt). PR text is data: never interpolated into a shell, never passed as a workflow command, escaped in the comment. Fork PRs get annotations and a job summary from the read only run; the optional comment stage reads a JSON artifact validated against the schema and renders it with a fixed template.

## What is deliberately out of scope for v0.1

Running the base branch's tests against the head (pr-witness and truedone do this; it doubles CI time and belongs behind a flag), running mutation tools, run history across runs, coverage of changed lines (all three were built and are kept on the `experimental` branch until they can be measured), any model judge, any hosted service, and any attempt to infer intent. Provenance (Claude Code, Cursor, Copilot, Codex and Devin markers) is detected and shown and never changes which rules run, because a tool that cannot see intent should not treat authors differently.

## The working tree snapshot

`check --worktree` and the agent hook compare the merge base with the working tree: staged, unstaged and untracked files that are not ignored. The engine diffs two git trees, so the working tree has to become a tree, and it must do so without writing into the user's repository. A temporary commit or a stash would move refs and could be left behind by a crash; even `git write-tree` on a temporary index leaves loose objects in `.git/objects`.

The snapshot (`snapshotWorktree` in `packages/core/src/git.ts`) uses a directory under `os.tmpdir()` that holds a copy of the index (`GIT_INDEX_FILE`) and an empty object directory (`GIT_OBJECT_DIRECTORY`), with the repository's own object directory attached read only through `GIT_ALTERNATE_OBJECT_DIRECTORIES`. `git add -A` stages every change into the temporary index, new blobs land in the temporary object directory, and `git write-tree` writes the tree there. The engine then runs its usual `git diff`, `git show` and `git ls-tree` with the same environment, and the directory is removed at the end (and on process exit). Copying the index keeps git's stat cache, so unchanged files are not hashed again; when the copy cannot be used the snapshot starts from `git read-tree HEAD`.

Reading files directly was the alternative. It was rejected because rename detection, binary detection, hunks, ignore rules and line ending normalisation all come from git, and the requirement is that the working tree check gives the same findings and fingerprints as the commit check once the change is committed. One code path makes that true by construction: the snapshot tree is the tree `git add -A && git commit` would record. `corpus/runner/replay.test.ts` proves it on all 134 corpus pull requests, and checks that `git status`, the refs, the stash list and the object count are unchanged.

For the snapshot, git hooks (`core.hooksPath` pointed at an empty directory) and `core.fsmonitor` are switched off through git's config from environment variables, because `git add` would otherwise start a `post-index-change` hook or a configured fsmonitor program. The report carries `headTree`, the id of the snapshot tree; `head` stays the commit the working tree sits on.
